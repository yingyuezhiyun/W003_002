# 模式控制架构设计（先设计后实现）

## 1. 设计目标

- 满足实时性：基于 0.1 ms 时基，执行路径可预测、可审计。
- 模式切换严格受控：必须先完成一次成功标定，才能进入位置/压力模式。
- 可调试：模式切换、拒绝原因、超时与故障都可观测。
- 可维护：职责分层清晰，避免跨层直接耦合。
- 可扩展：新增模式时，不需要改调度主干和底层驱动主流程。

## 2. 运行约束与输入来源

- 电机控制统一通过 `ElmoOps->xxx`。
- 反馈解析来自 CAN 中断或通信轮询。
- 命令输入来源明确为四类：
  - 外部串口命令。
  - EtherCAT 命令。
  - 按键输入（可在主循环中判断）。
  - TTL 电平输入（可在主循环中判断）。
- 主循环周期查询：
  - 标定模式：每 50 ms 查询位置/电流/速度。
  - 位置模式：每 50 ms 查询位置/电流。
- 压力模式快环：
  - 以 0.1 ms 时基驱动。
  - 每 9 ms 触发一次压力控制周期。
- 标定超时：2 分钟。

## 3. 分层架构

### 3.1 命令接入层（Command Ingress）

职责：
- 将串口、ECAT、按键、TTL 的输入统一转换为内部命令。
- 做最小必要的输入整形（按键/TTL 去抖、边沿检测、简单合法性校验）。
- 不直接执行业务动作，不直接切模式。

输出：
- 向模式监督层投递 `ModeCommand`（建议队列化）。

### 3.2 时基与调度层（Scheduler）

职责：
- 维护 0.1 ms 软时钟。
- 生成周期触发事件（例如 `EVT_50MS`、`EVT_9MS`）。

规则：
- ISR 只做计数和置位，快速返回。
- 较重逻辑在主循环执行，保证实时抖动可控。

### 3.3 模式监督层（Mode Supervisor）

职责：
- 维护顶层模式状态机。
- 统一执行切换守卫（guard）。
- 将命令/事件分发到当前活动模式模块。
- 维护共享上下文、监测快照、错误码和转移追踪。

### 3.4 模式模块层（Mode Modules）

职责：
- 各模式内部独立状态机与动作实现。
- 模式模块不直接改全局模式，仅通过监督层 API 申请切换。

模块：
- `mode_calib`（内部子状态机）
- `mode_position`
- `mode_pressure`

### 3.5 执行器适配层（Hardware Adapter）

职责：
- 将模式语义动作映射为 `ElmoOps` 调用。
- 将硬件调用细节隔离在适配层，减少模式逻辑对驱动细节依赖。

### 3.6 状态处理与错误监测层（Status & Error Monitor）

职责：
- 汇总系统状态、模式状态、故障状态。
- 提供错误监测预留点（如 LED 指示、告警上报）。
- 支持主循环无侵入查询。

说明：
- 本层先预留接口与结构，不在本阶段实现具体硬件动作。

## 4. 顶层模式状态机

建议状态：
- `MODE_BOOT`
- `MODE_CALIB`
- `MODE_POSITION`
- `MODE_PRESSURE`
- `MODE_FAULT`（预留）

核心守卫：
- 仅当 `calib_passed_once == true` 时，允许 `MODE_CALIB -> MODE_POSITION/PRESSURE`。
- 标定运行过程中，禁止切出标定模式。
- `MODE_POSITION <-> MODE_PRESSURE` 可双向自由切换。

建议转移表字段：
- `from_mode`
- `event_or_command`
- `guard_fn`
- `action_fn`
- `to_mode`

采用表驱动可减少层层分支，后续审计与调试更直观。

## 5. 标定子状态机

建议子状态：
- `CAL_WAIT_TRIGGER`
- `CAL_MOVE_TO_MIN`
- `CAL_CAPTURE_MIN`
- `CAL_MOVE_TO_MAX`
- `CAL_CAPTURE_MAX`
- `CAL_VERIFY`
- `CAL_SUCCESS`
- `CAL_FAIL`
- `CAL_TIMEOUT`

行为映射：
- 启动时设置低速。
- 下发较小位置指令，按电流/速度阈值识别末端并记录。
- 下发较大位置指令，按电流/速度阈值识别末端并记录。
- 校验行程阈值。
- 成功/失败/超时都恢复正常速度。

超时策略：
- 标定开始时记录起始 tick。
- 所有活动子状态优先检查超时。

## 6. 位置模式设计

职责：
- 接收任意目标位置命令。
- 接收全开/全关命令。
- 每 50 ms 查询位置和电流。

规则：
- 命令消费幂等：消费后清除请求位。
- 监测区记录命令来源、最后一次目标值与应用结果。

## 7. 压力模式设计

职责：
- 接收目标压力命令。
- 每 9 ms 执行一次压力控制周期。
- 在压力模式中获取位置反馈作为算法输入。

规则：
- 快环路径保持确定性，避免 ISR 内重逻辑。
- 若算法复杂度升高，采用分裂执行：
  - ISR 仅置 `pressure_loop_due`。
  - 主循环尽快执行算法体。

## 8. 数据模型建议

`ModeCommand`：
- 命令 ID。
- 数值负载（int32/float）。
- 命令来源（UART/ECAT/KEY/TTL）。
- 可选序号（用于跟踪丢包与覆盖）。

`ModeMonitor`：
- 当前顶层模式。
- 当前标定子状态。
- 标定完成/成功标志。
- 最近一次切换拒绝原因。
- 模式进入时间戳。
- 系统运行 tick。
- 计数器：切换次数、拒绝次数、超时次数、故障次数。

`TransitionTrace` 环形记录项：
- tick。
- from mode。
- to mode。
- 触发事件/命令。
- guard 判定结果。

## 9. 状态处理与错误监测预留点

预留接口建议：
- `ModeStatus_Update()`：汇总当前状态（主循环调用）。
- `ModeError_Update()`：错误检查入口（主循环调用）。
- `ModeIndicator_SetLed(pattern)`：LED 指示预留接口。
- `ModeFault_Report(code, source)`：故障上报预留接口。

建议预留的 LED 语义（仅定义，不实现）：
- 常亮：模式稳定运行。
- 慢闪：等待标定触发。
- 快闪：标定进行中。
- 双闪：故障或模式切换被拒绝。

说明：
- 本阶段只预留结构体字段、枚举和调用钩子，不实现硬件驱动动作。

## 10. 调试与维护策略

必须具备：
- `ModeCtrl_GetMonitor()` 只读快照。
- `ModeCtrl_ReadTrace()` 无阻塞读取状态转移记录。
- 错误/拒绝原因使用枚举，避免魔法数字。

收益：
- 快速定位“无法切模式”的根因。
- 现场问题可复盘、可对比。
- 后续重构更安全。

## 11. 文件组织建议

- `Core/inc/mode_ctrl.h`：仅公开 API 与必要公开枚举。
- `Core/src/mode_ctrl/mode_ctrl_internal.h`：私有上下文与内部类型。
- `Core/src/mode_ctrl/mode_supervisor.c`：顶层 FSM、守卫、命令分发。
- `Core/src/mode_ctrl/mode_calib.c`：标定子状态机。
- `Core/src/mode_ctrl/mode_position.c`：位置模式模块。
- `Core/src/mode_ctrl/mode_pressure.c`：压力模式模块。
- `Core/src/mode_ctrl/mode_diag.c`：监测与追踪实现。

若当前构建配置暂不便拆文件，可先单文件分区，但保持上述逻辑边界。

## 12. 增量迁移计划

阶段 1：
- 冻结公开 API 与监测结构。
- 引入命令队列与转移追踪环形缓存。

阶段 2：
- 顶层切换策略迁移为“表驱动 + guard”。
- 模式内部动作先保留空实现桩。

阶段 3：
- 将标定流程完全迁移为显式子状态机。

阶段 4：
- 增加状态处理与错误监测钩子（含 LED 接口预留）。
- 视需要引入 `MODE_FAULT` 及恢复策略。

## 13. 架构完成判定（DoD）

- 顶层模式切换为表驱动并具备守卫判定。
- 标定流程具备显式子状态转移与超时处理。
- ISR 工作量受控且执行确定。
- 主循环可读取监测快照与状态转移记录。
- 状态处理/错误监测预留接口齐备（含 LED 钩子）。
- 新增模式只需要：
  - 新增一个模式模块。
  - 新增一条模式注册项。
  - 更新转移表与守卫规则。
